# PROJECT CONTEXT — Automated Network Intrusion Detection System for Linux Networks

## 1. Project title

Automated Network Intrusion Detection System for Linux Networks

## 2. Purpose

Build a Linux-based network intrusion detection system (IDS) that:
- Captures/receives network traffic.
- Extracts and preprocesses network features.
- Uses machine learning to classify traffic as normal or malicious.
- Uses SHAP/LIME to explain ML predictions.
- Calculates a risk score and threat level.
- Provides a controlled automated threat-response module.
- Shows detections, explanations, risk, alerts, and response status in a real-time web dashboard.

The final visible product is a dashboard/web application, but it must be connected to the actual backend detection pipeline rather than displaying fake results.

## 3. Source project requirements

The project presentation proposes this data flow:

Traffic
→ Feature Extraction
→ ML Detection
→ SHAP/LIME
→ Linux Log Correlation
→ Risk Score
→ Automated Response
→ Dashboard

The proposed modules are:
1. Traffic Collection
2. Data Preprocessing
3. Intrusion Detection Model
4. Explainable AI
5. Threat Response & Dashboard

The project abstract proposes:
1. SHAP/LIME explanations.
2. Real-time dashboard for monitoring and alerts.
3. Linux log correlation with network packet analysis.
4. Automatic risk scoring.
5. Automated threat response for lower-level attacks such as port scans, SSH brute-force attempts, and SYN flood attacks using iptables/UFW while notifying the administrator.
6. Evaluation using Accuracy, Precision, Recall, and F1-score.

## 6. Dashboard goals

The dashboard should eventually display information such as:
- Network/system monitoring status
- Recent traffic/events
- Normal vs malicious classification
- Attack type
- Source IP / relevant network information
- Risk score
- Risk level: LOW / MEDIUM / HIGH / CRITICAL
- SHAP/LIME explanation of important features
- Alerts
- Automated-response status
- Blocked/suspicious IP information when applicable

The dashboard should show real data generated by the system.

## 7. ML goals

Start with a practical baseline model rather than overcomplicating the project.

Preferred initial model:
- Random Forest

Possible later comparison/extension:
- XGBoost

Training/evaluation should use the CICIDS2017 dataset if practical.

Required evaluation metrics:
- Accuracy
- Precision
- Recall
- F1-score

Do not claim an accuracy/result unless it has actually been measured from the implemented system.

## 8. Explainable AI goals

For an individual prediction, the system should be able to answer:

"Why did the model classify this traffic as malicious?"

SHAP and/or LIME should identify important contributing features.

Example conceptual output:
- High packet count contributed strongly.
- Unusual flow duration contributed.
- Unusual destination port contributed.

Do not fabricate explanations. Explanations must come from the actual model/XAI output.

## 9. Risk scoring

Create a transparent risk-scoring mechanism that maps detected events to:
- LOW
- MEDIUM
- HIGH
- CRITICAL

The scoring logic should be simple, documented, reproducible, and easy to explain during a project presentation.

Do not pretend that the risk score is produced by AI unless the implementation actually does that.

## 10. Automated response

The proposed response module can use Linux firewall mechanisms such as UFW/iptables.

IMPORTANT:
- Develop and test the response module safely.
- Do not blindly block real IP addresses on the user's machine.
- Prefer a controlled/local test environment.
- Make destructive/firewall-changing operations explicit and require user confirmation where appropriate.
- Keep a log of response actions.
- Provide a dry-run/test mode before enabling real firewall changes.

Example conceptual flow:

Attack detected
→ Risk calculated
→ Response policy checked
→ Alert/log
→ Controlled firewall action if policy permits
→ Dashboard updated

Milestone 11 — Flask dashboard
